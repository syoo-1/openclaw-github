# 安检器 Skill v0.1

## 人话别名
- 安检器
- 外来对象安检器
- 外来项目安检器

## 人话触发
当用户表达以下意思时，默认启用本卡：

- 小一，用安检器检查一下 XXX
- 近一，用安检器检查一下 XXX
- 检查一下这个 skill 安不安全
- 检查一下这个 app 能不能用
- 检查一下这个 GitHub 项目能不能装
- 检查一下这个 MCP 工具有没有风险
- 这个安装命令能不能跑
- 这个插件会不会污染系统
- 这个项目会不会乱用 token
- 这个工具能不能接入 Core / PG

默认动作：
- 先进入安检区
- 默认只读扫描
- 默认不安装
- 默认不运行
- 默认不接 Core / PG / 02-brain
- 默认不写 System-Snapshots 正式层

## 1. 主类型 / 次类型
- 主类型：检查型
- 次类型：监管型

## 2. 目标
对外来 skill、app、GitHub 项目、MCP 工具、脚本、插件、安装命令进行接入前安检，判断其安全性、可用性、系统污染风险、账号/token 风险，并给出 A / B / C / D 四级结论。

## 3. 适用场景
适用于：
- 从 GitHub 找到新项目后
- 准备安装外来 app / 插件 / MCP 工具前
- 准备测试别人提供的脚本或安装命令前
- 准备把某个工具接入 Core / PG 前
- 准备把某个查新结果沉淀为知识摘要前
- 用户明确要求“用安检器检查一下”时

不适用于：
- 直接替代用户安装项目
- 直接运行未知脚本
- 直接执行 curl | bash
- 直接把外来项目写入 Core / PG / 02-brain
- 在没有对象、没有链接、没有文件内容时空转判断

## 4. 输入
可接受以下任一对象：

1. GitHub URL
2. 项目目录
3. README 文本
4. package.json / pyproject.toml / requirements.txt / Dockerfile / Makefile / install.sh
5. MCP 配置片段
6. app 下载页或说明页
7. 外来 skill 文本
8. 安装命令
9. 用户贴出的项目说明或日志

若输入不足，只能标注“未知”，不得把未知项默认判为安全。

## 5. 输出
必须输出以下内容：

1. 安检结论：
   - A：安全
   - B：可控
   - C：不建议
   - D：危险

2. 可用性判断：
   - 可测试
   - 暂缓测试
   - 不建议测试
   - 禁止运行

3. 安全简述：
   - 用人话说明为什么这样判

4. 风险清单：
   - 系统污染风险
   - 权限风险
   - 账号 / cookie / session 风险
   - API Key / Token 风险
   - 网络访问风险
   - 数据外传风险
   - 维护状态风险
   - 依赖风险

5. 未知项清单：
   - 查不出来的项目必须标“未知”

6. 下一步建议：
   - 是否可进外挂区
   - 是否需要手动分步测试
   - 是否禁止接 Core / PG / 02-brain
   - 是否可生成知识摘要

## 6A. 安检等级定义

### A：安全
含义：
- 当前只读扫描未发现明显高危行为
- 安装方式清楚
- 权限边界清楚
- 不强制 sudo
- 不明显读取密钥、cookie、session、浏览器数据
- 不明显写启动项
- 不明显修改 shell 配置
- token 使用可控或无外部模型调用

限制：
- A 只代表可以进入外挂区
- A 不代表可以直接接入 Core / PG / 02-brain
- A 不代表已经完成代码级安全审计

### B：可控
含义：
- 有一定风险，但边界可控
- 可以手动分步测试
- 需要隔离目录
- 不能自动安装
- 不能直接接主系统

常见原因：
- 需要 API Key
- token 消耗不完全明确
- 有网络访问
- 依赖较多
- 需要局部配置
- 维护状态一般但仍可读

### C：不建议
含义：
- 风险不清
- 资料不足
- 维护差
- 安装方式混乱
- 权限边界不清
- token / 数据外传风险未知且不可控

处理：
- 暂不测试
- 先补资料
- 不进入主系统
- 不生成正式知识，只能留安检报告

### D：危险
含义：
- 发现明显高危行为，直接拦截

常见触发：
- 要求 sudo 且理由不清
- curl | bash
- 自动修改 ~/.zshrc / ~/.bashrc
- 自动写入 ~/Library/LaunchAgents
- 自动全局 npm / pip 安装且不可控
- 读取 ~/.ssh
- 读取浏览器 cookie / session
- 自动上传本地文件
- 自动外传 prompt / response / 密钥
- 自动写入 System-Snapshots / Core / PG / 02-brain
- 安装脚本混淆或不可读
- 项目来源明显可疑

## 6B. 必查指标
每次安检至少检查以下项目：

1. 项目用途
2. 来源可信度
3. 维护状态
4. 安装方式
5. 是否全局安装
6. 是否修改系统配置
7. 是否写入启动项
8. 是否要求 sudo
9. 是否要求 API Key / Token
10. 是否可能产生高 token 消耗
11. 是否有 token 限额控制
12. 是否记录 prompt / response
13. 是否会把用户内容发送到外部模型
14. 是否读取 cookie / session / 浏览器数据
15. 是否读取 ~/.ssh 或系统密钥
16. 是否访问网络
17. 是否能在隔离目录运行
18. 是否可能碰 System-Snapshots / Core / PG / 02-brain
19. 是否有卸载方式
20. 是否有日志、缓存、临时文件残留

查不出来的项目统一标：
- 未知

不得把“未知”说成“安全”。

## 7. 执行步骤

1. 明确安检对象。
2. 若对象是链接，先读取公开说明；若无法读取，要求用户提供 README 或关键文件内容。
3. 若对象是本地目录，只读查看关键文件，不运行。
4. 优先检查：
   - README
   - package.json
   - pyproject.toml
   - requirements.txt
   - Dockerfile
   - Makefile
   - install.sh
   - setup.py
   - 配置样例
   - 启动脚本
5. 对照必查指标逐项扫描。
6. 标出未知项。
7. 给出 A / B / C / D 结论。
8. 给出一句话安全简述。
9. 给出下一步建议。
10. 如有可沉淀经验，只生成 knowledge 摘要建议，不直接写入 02-brain。

## 8. 调用能力
- 文件：按需
- 浏览器 / 联网查新：按需
- 对照 02 规则：按需
- 对照 03 工艺规则：按需
- 运行外来脚本：禁止
- 自动安装：禁止
- 自动接入 Core / PG：禁止
- 自动写 02-brain：禁止

## 9. 安检区
公共安检区固定为：

`~/安检区`

目录结构：

- `~/安检区/待检区`
- `~/安检区/外挂区`
- `~/安检区/安检报告`
- `~/安检区/拦截记录`
- `~/安检区/知识摘要`

规则：
- PG 可调用
- Core 可调用
- 安检区不是主脑
- 安检区不是正式知识层
- 安检报告先进入 `安检报告`
- 可复用经验摘要进入 `知识摘要`
- 是否进入 02-brain 必须另行筛选

## 10. 知识沉淀规则
查新结果可以成为大脑知识层的一部分，但不能原样进入。

正确流程：

1. 原始扫描结果进入 `~/安检区/安检报告`
2. 可复用经验提炼为摘要，进入 `~/安检区/知识摘要`
3. Core / PG 判断是否值得进入 02-brain
4. 通过筛选后，才允许进入正式知识层

允许沉淀：
- 某类工具的共性风险
- 某个平台的典型安装坑
- 已验证过的安全判断标准
- 某个项目的最终安检结论
- 后续可复用的经验

不允许直接沉淀：
- 大段 README 原文
- 临时日志
- 每次扫描完整报告
- 未验证猜测
- 一次性路径、缓存、报错碎片

## 11. 成功标准
- 明确说明安检对象
- 明确说明已检查什么
- 明确说明未知什么
- 给出 A / B / C / D 结论
- 给出安全简述
- 给出可执行下一步
- 不把可运行说成安全
- 不把 A 级说成可直接接主系统
- 不把未知项冒充已验证

## 12. 失败回退
- 对象不清：要求补对象或链接
- 链接打不开：要求用户提供 README / 关键文件
- 文件不足：只做初检，结论不得高于 B
- token 风险查不出：标“未知”
- 权限风险查不出：标“未知”
- 安装脚本不可读：至少 C；若混淆明显，判 D
- 发现高危动作：立即 D，停止继续推进

## 13. 风险点
最容易误判的地方：

1. 把 GitHub 星标多误判为安全
2. 把项目能运行误判为可接主系统
3. 把 README 写得漂亮误判为维护可靠
4. 漏检 install.sh / postinstall / Makefile
5. 漏检 npm / pip 的全局安装
6. 漏检 token 消耗
7. 漏检 prompt / response 日志外传
8. 漏检 cookie / session 风险
9. 漏检 LaunchAgent / 后台服务
10. 把未知项默认当安全

## 14. 验证方式
用 3 类对象试跑：

1. 一个简单 GitHub README 项目
2. 一个需要 API Key 的 MCP 工具
3. 一个含安装脚本的 app / CLI 工具

检查是否能稳定输出：
- A / B / C / D
- 已检查项
- 未知项
- 风险点
- 下一步建议

## 15. 标准回报格式

### 简版
安检结果：B 可控

一句话：
功能有用，但需要 API Key，token 消耗未知，只能进外挂区，不能接 Core / PG / 02-brain。

下一步：
放入 `~/安检区/外挂区` 手动分步测试。

### 完整版
安检对象：
- XXX

结论：
- 等级：B 可控
- 可用性：可测试
- 安全性：中等风险

已检查：
- README
- package.json
- 安装说明

未知项：
- token 消耗上限未知
- 是否记录 prompt / response 未知

主要风险：
1. 需要 API Key
2. 有外部网络访问
3. 依赖较多

安全简述：
该项目功能方向可用，但存在外部模型调用和 token 成本不明问题。当前只能隔离测试，不得接入主系统。

建议：
- 允许进入 `~/安检区/外挂区`
- 禁止自动安装
- 禁止接 Core / PG / 02-brain
- 测试后再决定是否生成知识摘要
